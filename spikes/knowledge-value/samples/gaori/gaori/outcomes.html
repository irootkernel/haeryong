A command failure and an evidence failure answer different questions

How do child-command failure, extraction failure, artifact failure, and parser miss differ? What happens when child exit 0 or child exit 7 is followed by the same extraction internal error? How does standalone summarize differ when no child was executed?

With successful artifact materialization, child 0 followed by an extraction internal error predicts internal_error / 0 / degraded in summary and status, with CLI exit 4. Child 7 followed by that error predicts failed / 7 / degraded, with CLI exit 7. Standalone summarize followed by an extraction internal error predicts internal_error / 4 / degraded, with CLI exit 4; it has no authoritative child execution result. A parser miss follows a different evidence-quality branch. An artifact error can prevent completion of the artifact set.

G05 · Direct source

A specialized parser miss is not an internal error

When no project rule matches, a specialized parser miss does not retry generic extraction: after a passing command it yields passed/0 with no_match and CLI exit 0; after an authoritative non-pass result it preserves that result with degraded extraction.

For the ordinary child-7 case, the documented miss branch therefore predicts failed / 7 / degraded and CLI exit 7. A missed failure span cannot turn a failing command into a pass. G-S19 · architecture:607–614

G06 · Direct source

Degraded does not identify one cause

extractor_status degraded alone does not establish an extraction internal error: bounded-tail extraction and evidence truncation can also produce degraded after a passing command while preserving passed/0 and CLI exit 0.

Read command status, command exit code, extraction quality, and available diagnostics together. A bounded-tail scan can find useful evidence while omitting earlier evidence. The documented extraction-error diagnostic is bounded and configured-redaction-aware, goes to stderr, and is not added to the JSON schemas; this directory supplies no actual diagnostic. G-S01 · Child wait classification

gaori@393af5999bbbb30b5d11e2a17a2325c8cf1833b7:internal/runner/runner.go:250–269

func classifyWait(output model.RunOutput, err error) (model.RunOutput, error) {
	if err == nil {
		output.Status = model.RunStatusPassed
		output.Metadata.ExitCode = 0
		return output, nil
	}

	var exitErr *exec.ExitError
	if errors.As(err, &exitErr) {
		if ws, ok := exitErr.Sys().(syscall.WaitStatus); ok && ws.Signaled() {
			output.Status = model.RunStatusKilled
			output.Metadata.ExitCode = signalExitCode(ws.Signal())
		} else {
			output.Status = model.RunStatusFailed
			output.Metadata.ExitCode = exitErr.ExitCode()
		}
		return output, nil
	}

	return model.RunOutput{}, model.NewGaoriError(model.ExitCodeParserError, "execute command", err)

func WriteSummaryJSON(paths model.ArtifactPaths, summary model.Summary) (string, error) {
	data, err := marshalSummaryJSON(summary)
	if err != nil {
		return "", model.NewGaoriError(model.ExitCodeArtifactError, "marshal summary json", err)
	}
	written := append(data, '\n')
	if len(written) > safety.MaxSummaryBytes {
		return "", model.NewGaoriError(model.ExitCodeArtifactError, "write summary json", fmt.Errorf("summary json exceeds %d bytes", safety.MaxSummaryBytes))
	}
	if err := writeArtifact(paths, paths.SummaryJSON, written, "write summary json"); err != nil {
		return "", err
	}
	return SHA256(written), nil

G-S15 · Accepted command-authority decision

gaori@393af5999bbbb30b5d11e2a17a2325c8cf1833b7:docs/architecture-decision-records/README.md:45

`internal_error` is reserved for a Gaori evidence-pipeline failure when no authoritative non-pass command result must be retained. If extraction fails after a command exited `0`, summary and status artifacts keep `exit_code: 0`, use `status: internal_error` and `extractor_status: degraded`, and the Gaori process exits `4`. If the command already failed, timed out, or was killed, that state and exit code remain authoritative. Standalone summarize has no authoritative execution result, so an extraction internal error uses `status: internal_error` and exit code `4` in its artifacts and exits `4`.

G-S19 · Extraction policy and outcome matrix

gaori@393af5999bbbb30b5d11e2a17a2325c8cf1833b7:docs/architecture/README.md:601–603

- Execution and summarize logs larger than 256 KiB are extracted from at most the final 256 KiB, beginning at the first complete line in that window. Spans retain absolute line and byte offsets into the full raw log.
- A bounded-tail scan always reports `extractor_status: degraded`, even when it finds useful evidence, because earlier evidence may have been omitted.
- Failure or warning record truncation always reports `extractor_status: degraded`; command status and exit code remain authoritative.

- Parser or rule matches and misses never convert an authoritative non-pass result into pass.
- Project rules run before the selected parser. When no rule matches, a specialized parser uses only its own patterns and never retries generic extraction.
- Tagged ad-hoc runs may select that parser explicitly; configured runs continue to use only their configured parser.
