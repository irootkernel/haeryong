A finished invocation is terminal; a waiter ending is not

A waiter times out, cancel_run says accepted:true, or the MCP connection disappears. Which observation is terminal, when can the same invocation be awaited, and when is another start unsafe?

Inspect the invocation's finished phase and its final result or error. Wait expiry and cancellation acceptance do not establish completion. After an await request ends, the same ID may be awaited again in the surviving server session. After disconnection, reconcile the original command and final artifacts before retrying; another server cannot recover the old invocation.

G07 · Direct source

Finished settles the invocation, not necessarily a passing check

The shown finish method sets phase finished, records a result or error, and closes the completion event; terminal completion therefore does not by itself mean command success.

A non-nil result supplies the finalized summary path; a Gaori error is stored separately. Inspect the final result or error rather than treating the lifecycle phase as a passing status. The accepted MCP decision also distinguishes a test failure carried in a successful exchange from a protocol failure. G08 · Direct source

A revision wait expiry is only an observation boundary

When wait_run's timer expires, the shown implementation returns the current snapshot with changed:false; expiry alone neither establishes a finished phase nor creates a command timed_out result.

Inspect the returned phase. A concurrent finish can already be visible in that snapshot, so changed:false is not proof that the invocation is still running either. The public tool describes a wait of up to 50 seconds without cancelling the run. With after_revision greater than the current revision, the implementation returns an input error rather than waiting. G09 · Direct source

Await can resume against the same surviving session

Cancelling or timing out an await_run request ends only that waiter; the invocation keeps running and the same session-local ID may be awaited again while its original server session remains available.

await_run has no Gaori-owned timeout argument. It returns immediately for an already finished invocation, otherwise waiting for the completion event or the request context to end. A host deadline must cover command execution and expected evidence materialization if one uninterrupted wait is required. This does not authorize a new start when only the waiter ended. G11 · Direct source

Disconnection does not produce a recoverable durable job

Gaori's live invocation registry belongs to one MCP server process and is not recovered after restart; completed on-disk list_runs entries carry no invocation ID and cannot be awaited as live invocations.

The integration guide requires reconciliation of the command and final artifacts after a disconnect. Connection loss alone is not a terminal command result. The supplied shutdown description includes active-run cancellation and bounded artifact draining; it does not establish that every abrupt disconnection leaves a complete artifact set. Read-only finished evidence and live session operations have different identities. G-S16 · ADR-0012:253–260 G-S17 · ADR-0018:413 G-S14 · mcp.go:637 G-S18 · integration-guide.md:298

G12 · Qualified inference

Resolve the original outcome before a replacement start

A waiter timeout, accepted cancellation, or disconnect alone is insufficient grounds for a replacement start: reconcile the original invocation, or its command and final artifacts, before deciding whether another execution is needed.

The risk is an unresolved prior execution, not proof that duplication has already happened. The integration guide says to retain the original invocation or process identity after starting rather than rerun to switch transports, and to reconcile command and final artifacts before retrying after disconnection. A surviving correctly bound session permits awaiting the same ID. If that session is gone, a new server cannot restore that ID. Missing artifacts alone do not prove that the original command never executed. G-S18 · integration-guide.md:298 G-S17 · ADR-0018:411–413, 420

func (i *mcpInvocation) finish(result *runResult, err error, redactor *safety.Redactor, repoRoot string) {
	i.mu.Lock()
	defer i.mu.Unlock()
	i.snapshot.Phase = mcpPhaseFinished
	i.snapshot.Result = result
	if result != nil {
		i.finalizedSummaryPath = canonicalMCPPath(repoRoot, result.SummaryJSON)
	}
	if err != nil {
		i.snapshot.Error = &mcpRunError{ExitCode: model.ExitCodeFor(err), Message: safeMCPErrorMessage(err, redactor)}
	}
	i.bumpLocked()
	close(i.done)

G-S10 · Cancellation request guard

gaori@393af5999bbbb30b5d11e2a17a2325c8cf1833b7:internal/cli/mcp.go:131–141

func (i *mcpInvocation) requestCancel() bool {
	i.mu.Lock()
	defer i.mu.Unlock()
	if i.snapshot.Phase == mcpPhaseFinished || i.snapshot.CancellationRequested {
		return false
	}
	i.snapshot.CancellationRequested = true
	i.bumpLocked()
	i.startGate.Cancel(i.cancel)
	return true
}

func (m *mcpManager) await(ctx context.Context, id string) (mcpSnapshot, error) {
	inv, err := m.lookup(id)
	if err != nil {
		return mcpSnapshot{}, err
	}
	inv.mu.Lock()
	if inv.snapshot.Phase == mcpPhaseFinished {
		snapshot := inv.snapshot
		snapshot.Changed = false
		inv.mu.Unlock()
		return snapshot, nil
	}
	done := inv.done
	inv.mu.Unlock()
	select {
	case <-done:
		return inv.read(), nil
	case <-ctx.Done():
		return mcpSnapshot{}, ctx.Err()
	}

G-S16 · Accepted session-local boundary

gaori@393af5999bbbb30b5d11e2a17a2325c8cf1833b7:docs/architecture-decision-records/README.md:253–255

Gaori will expose a STDIO-only MCP server with an in-memory invocation registry. A start operation returns immediately; get and revision-based wait operations expose `queued`, `executing`, `materializing`, and `finished` phases; explicit cancel and server shutdown cancel active child process groups. Wait expiry and cancellation affect only the wait request. Completed results reuse the existing command, extraction, redaction, and artifact contracts, and raw-log contents are never returned through MCP.

This live channel is scoped to one MCP server process. It does not persist running state, recover invocations after restart, detach commands, listen on a network socket, or own workflow and acceptance state. ADR-0016 clarifies that this session-state boundary does not restrict read-only MCP access to already-materialized on-disk evidence. ADR-0005 remains the compatibility boundary for final filesystem watchers.

The wait-request wording concerns cancellation of a waiter; explicit run cancellation is separately described in G-S12, G-S13, and G-S17.

G-S17 · Accepted terminal-await decision

gaori@393af5999bbbb30b5d11e2a17a2325c8cf1833b7:docs/architecture-decision-records/README.md:409–413

Gaori will add a read-only, idempotent `await_run` MCP tool that accepts only an invocation ID. It returns immediately with the existing terminal snapshot when the invocation is already `finished`; otherwise it waits on that invocation's immutable completion event until `finished` or until the tool request context ends. The tool adds no Gaori-owned timeout argument. Hosts that want one uninterrupted wait must configure their MCP tool deadline to cover the selected command timeout and expected local evidence materialization time.

Cancelling or timing out the `await_run` request cancels only that waiter. The invocation keeps running and the same session-local ID may be awaited again. Only `cancel_run` or MCP server shutdown cancels the run context. `wait_run` remains the bounded revision/phase-observation interface; `await_run` is the terminal-only interface. Both return the same authoritative final command status and bounded redacted derived evidence, and neither changes artifact, watcher, or extractor semantics.

Although `await_run` is annotated read-only, it is a live session-registry operation governed by ADR-0012, not the stateless finished-evidence read described by ADR-0016. It cannot address an invocation from another MCP server process or recover one after restart.

G-S18 · Original identity and disconnect reconciliation

gaori@393af5999bbbb30b5d11e2a17a2325c8cf1833b7:docs/integration-guide.md:298

Original-identity excerpt

Once a run starts, retain its original invocation or process identity rather than rerunning it to switch transports. For a correctly bound MCP server, start a run, then call `await_run` with only the returned invocation ID when terminal completion is the next required event.

Cancellation and shutdown excerpt, same line

Use `cancel_run` only for explicit cancellation. Its `accepted: true` means that call recorded the first cancellation request for an unfinished invocation; it does not guarantee a `killed` final result or stop evidence materialization. Repeated requests and requests after `finished` return false, and every caller must wait for `finished` before consuming the authoritative status and exit code. This avoids OS process polling but does not create durable state. Closing stdin at a newline-delimited frame boundary cancels active runs with exit `0`: after every in-flight process-start gate resolves and cancellation is delivered, the server drains artifacts for at most three seconds. The gate wait prevents late child creation and is not part of that drain budget. A truncated final frame exits `4`, while SIGINT/SIGTERM use the same shutdown ordering and exit `130`/`143`.

Disconnect excerpt, same line

If the MCP server disconnects, reconcile the command and final artifacts before retrying; a new server cannot recover the old invocation ID.

The shutdown exit numbers above describe the server shutdown paths in this excerpt; they are not reported child-command outcomes for a run in this directory.
