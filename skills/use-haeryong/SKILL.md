# Use Haeryong

Produce an inspectable explanation that answers the requested question, with complete files in the selected result directory. This is the one Haeryong-owned guidance source for compatible Aquarium and standalone hosts. Discover the current host and Haeryong capabilities before choosing a workflow; capability availability and actual receipts govern what can be claimed. Do not assume a global skill installation, an account, a CLI location or a live daemon.

## Discover the current workflow

Read the trusted host's supplied capabilities, current project/source/provider selection, operation identity, explicit publication or draft intent, and output ownership. Use available library search and inspect relevant exact prior versions before rebuilding an explanation. Keep their immutable document/version/page/region identities; source-check material claims rather than treating a prior explanation as source evidence. If a selection is absent, resolve it through the host's current remembered-selection interface. A scoped workflow uses its authorized selected project; an owner-authenticated launcher may resolve an unselected new-document request through its normal Unfiled association. Never fall back to another target to make a denied or mismatched request succeed.

When the host supplies `consumer: managed-generation`, its output directory is the complete candidate destination. Write the files there and return the directory and useful page paths. The host owns saved-result capture, validation and guarded atomic publication/draft application. Do not separately run `haeryong import`, issue another generation, or publish through another channel for that same request.

For an external compatible host, discover its supported Haeryong CLI/API and remembered scoped workflow credential. The trusted launcher handles owner-authenticated local grant issuance/rotation; no owner bearer, polling secret or management authority belongs in generation context or artifacts. For an explicit direct-publication request, the supported CLI form is `haeryong import DIRECTORY --project PROJECT --new-document --operation-id UUID`, or `--document DOCUMENT --base-version VERSION` for a captured existing-document base. Use the actual CLI help/capabilities to confirm the installed form and current authorized selections. Preserve the final operation key across response loss; transfer creation/sealing have their own automatically persisted preparation keys. A draft-only request uses the supported draft workflow, never this direct-publication command. If that consumer is unavailable, report the candidate files and limitation rather than silently publish.

Inspect current operations/jobs after an uncertain acknowledgement. Reconcile or consume an already saved complete result without reissuing the model request. An explicit new attempt uses a fresh candidate destination, never an old partial tree. A stale captured base leaves the ready candidate available for the owner's explicit next action; do not replace the base with latest on retry.

## Source and context

Reuse the owner's selected project, exact source revisions, disclosure scope and provider configuration. Read the relevant supplied source; a previous explanation is context, not independent source proof. Unchanged approved scope needs no repeated permission request. Report missing/denied inputs; an expanded source or billing scope needs the normal owner decision. Preserve normal owner tools, instructions, hooks and plugins without claiming that application scope creates an OS sandbox.

Distinguish directly supported source observations, qualified inference and conceptual illustration where each claim appears, including diagrams and JavaScript outcomes. Cite the exact repository/revision, path and relevant lines or supplied evidence identity. Quotes must match inspected bytes. Label assumptions and unavailable coverage locally; a hash change alone does not establish semantic outdatedness, and similar terminology does not prove a runtime dependency. Preserve the truth of an explanation about a fixed historical release.

Describe the source actually provided or inspected. Host receipts establish whether exact bytes were accepted as provider input: do not invent observed_input, native_observed, attempt IDs or read receipts. A later exact-source check is posthoc_verified and does not backdate original input observation or prove comprehension. Never include credentials, private account material or hidden reasoning in generated files.

## Explanation files

Choose useful pages and interactions for the reader's question. Use ordinary HTML/CSS/JavaScript, relative or root-relative links, modules, workers, frameworks or CDN resources when appropriate. Meaningful controls should reveal a branch, comparison or limitation with evidence; label a simulation as an illustration unless an actual trace supports it. Provide a readable explanation alongside the interaction.

Write only the selected result tree, which may be inside the owner’s project; do not overwrite unrelated source files. Preserve nested assets and exact filenames. Do not flatten, silently omit, truncate or inline everything to fit an invented quota. No mandatory index.html, author manifest, hashes, source metadata, region declarations or author SDK is required. Optional enrichment is separate from original file bytes; an ordinary manifest.json remains a payload file. Report actual platform or provider limits and incomplete output explicitly.

When useful, give page-local stable anchors and optional evidence links under the host's supplied convention. Region identity includes its exact page. For an inspected prior explanation, preserve the supplied immutable document/version/page/region target and enough local context to explain its relevance. Do not silently substitute latest, invent a missing target, or present a cross-project analogy as an established caller relationship. Missing optional references stay unresolved while ordinary pages remain readable.

## Deliver and revise

Return the actual output directory, useful page/anchor paths, source basis, external dependencies and incomplete or unverified portions. If import or display is unavailable, report files produced rather than claim an import. The trusted host owns credentials/native calls and any separately supported context integration; authored pages receive no management authority.

For a requested revision, retain the prior immutable explanation and produce a new complete candidate. Keep historical citations and explicitly rejected or pinned decisions distinct from a new assessment. A changed or partial input cannot yield an all-current verdict. Preserve failed outcomes and repair only the demonstrated problem within the assigned scope; do not replace a failed question with an easier one or retry an uncertain provider operation blindly.

Generation grants only the requested output and explicit publication/draft consumer. It does not authorize device approval, network exposure, policy changes, personal Reviewed status, purge, source edits or account/billing changes. Keep capability-unavailable Notes, saved Q&A, maintenance and second-device actions honest; do not invent saved records or completed workflows. Personal Review remains the owner’s version-specific action and is never inferred from a successful generation or import.
