## Sequential execution and task sizing

Execute the ten Epics in their explicit dependency order. Complete the current Epic's gate before starting the next Epic. TASK-001-07 deliberately runs after TASK-001-05 and before TASK-001-06; numeric task IDs are stable identities, not a sorting algorithm.

A bounded prototype can span the understanding workflow inside the current Epic when its scope and temporary adapters are recorded. TASK-001-01 prepares one concrete reader question and a short comparison using already authorized existing explanations/source evidence before costly spikes; it neither requires a new provider call nor passes G-VALUE. TASK-001-04 checks useful interaction on the actual viewer harness, and TASK-001-07 owns the two-project real-generation slice before contract freeze. None requires future production Epics to close its gate. Reuse the same questions in the progressive checkpoints in [knowledge quality](testing/knowledge-quality.md); add production notes, Q&A and remote behavior only when their owning features exist.

Task count follows coherent, reviewable outcomes. No fixed number of tasks per Epic is a quality rule. Split or combine oversized tasks by updating IDs, dependencies, completion_requires, the task index and traceability together. Keep one sequential handoff; review/test substeps do not authorize unrecorded future-Epic work. Separate true prerequisite dependencies from convenient implementation ordering when revising the plan.

## Status and gate semantics

Planning states are planned, ready, in_progress, blocked, in_review and done. All implementation tasks in this revision remain planned. The canonical test/gate evidence enum is `not_run`, `pass`, `fail`, `blocked`; all application evidence remains `not_run` until actually executed. Use `fail` with a repair reason instead of a separate needs-rework status. These evidence values are distinct from task planning states and runtime job states.

A task becomes ready when its predecessors and applicable gates pass. It becomes done only when its implemented outcome, task-specific checks and shared definition of done pass and review is recorded. An Epic becomes done only when every task in completion_requires is done and its exit gate passes. A record that merely exists, a recorded failure or an unresolved blocked check cannot close a gate.

EPIC-001 requires G-STACK, G-AUTH, G-VIEW, G-AI, G-VALUE and G-CONTRACT to have status `pass` for the selected current baseline. G-AUTH proves remembered one-owner access and revocation; G-VIEW proves useful JavaScript plus host DOM/token/native-bridge separation; G-AI proves one supported real provider, exact source claims and honest permissions. These are bounded practical checks, not certification of network isolation, every device platform or an external-agent OS jail. Provider eligibility preflight starts in TASK-001-01, the real scoped cited question remains TASK-001-05, and the two-project value prototype precedes contract freeze. A fixture, static fallback or document is not substituted for the specific real integration/interaction evidence. A blocked provider or environment proof stops the work that consumes it. Independent fixture preparation or bounded experiments inside the current Epic may continue as explicitly labelled preparatory evidence, including experiments relevant to a later Task. They do not start that Task's formal implementation, make it ready or done, satisfy its unmet predecessor, or close a gate. Record the active Task, experiment scope and missing proof; the owning Task reruns or validates the result after it becomes ready. This does not close EPIC-001 or start EPIC-002 production. If a supported route cannot be established, prepare the observed failure and supported alternatives for the owner's deployment/billing/scope decision; only an explicit revised baseline can change those obligations.

Inherited acceptance IDs indicate contribution until the complete scenario runs at its owning stage. The acceptance catalog and traceability table distinguish primary completion at that stage, early/additional contribution and release regression. M08/M14/M20 complete their Stage A scope by TASK-007-06; EPIC-010 repeats the proof for the release installation. Supplemental cases likewise distinguish early bounded evidence, first feature proof and later regression. A shared case's requirement set describes the whole case; each contributing task records only its implemented or verified portion, not every requirement of every other owner. Stage A requires C01–C09, M08, M10, M14 and M15–M20 under the acceptance catalog's current owner-amended applicability, on the selected real environment plus an available private second device and the knowledge-quality workflow. G-VIEW requires the exact pinned Wails build and actual private HTTPS Safari iOS/iPadOS proof specified by TASK-001-04, using the TASK-001-03 route. Missing required device or concurrent-version evidence is blocked; a primary-browser result alone does not pass it. Initial delivery targets remain those in decisions P-11 and the deployment support tiers; validate the functionality actually advertised for each target before claiming support. Additional combinations outside those declared targets stay unverified without blocking the initial scope. Superseded security assumptions are not hidden gate requirements.

## Shared definition of done

Every task record contains its unique inputs, work, deliverables, completion checks and exclusions. The following common rules apply once through this protocol:

- Required functional and focused host/session, recovery and concurrency cases pass against the implemented behavior. Use case IDs and fixture/source/device identities; task-local T-* IDs are assertion identifiers, not claims that runnable test commands already exist.
- Record the exact code revision, commands or manual procedures, environment, expected/observed outcome and evidence links. Label synthetic, fake-provider, real-provider, browser and physical-device evidence correctly.
- Contracts, examples, schemas and migrations agree. Classify data/compatibility effects and document a tested rollback or recovery path where state changes.
- Current owner authentication, immutable history, version-specific Review, remembered source/provider choices, durability and lifecycle integrity remain intact. Secrets, private source and hidden model reasoning do not enter public logs or committed evidence.
- For changed UI, exercise the named reader action with keyboard/touch and relevant screen states; record concrete failures instead of an unqualified usable result.
- An independent reviewer records the decision and remaining limits. Existing CI/PR artifacts can serve as evidence; do not write duplicate reports just to fill a template.

## Responsibilities and evidence

The implementing agent owns code, fixture preparation, self-checks and contract updates. A separate review agent or qualified reviewer checks the evidence and changed boundaries. Record the reviewer identity and whether an evaluation used an owner, another human or agents only. The owner supplies environment-specific authority and decisions that alter established product direction; routine implementation choices and fixes do not require repeated approval.

G-VALUE, generation/Q&A and semantic maintenance follow [knowledge quality](testing/knowledge-quality.md). Separate citation resolution from claim support, reader outcomes from performance, and sample findings from general accuracy claims. Owner feedback is valuable, but do not describe an agent-only walkthrough as a human usability study.

Use fake clocks, barriers, fake providers and synthetic repositories for deterministic cases. Seeded lifecycle/personal/configuration rows may prove filters, exact anchors or restore guards before the corresponding mutation/UI feature exists; record the bounded claim and the later production regression owner. A capability-disabled screen may be checked before its action ships, but it cannot claim that action works. Real provider/remote/native gates require actual evidence from the selected supported setup. Use small fixtures for host-boundary checks and disposable libraries for purge or recovery. Do not require an exhaustive attack corpus or every-platform test suite for this personal tool.

## Contract and dependency changes

Before freeze, refine proposed mechanisms using spike evidence. Freeze only evidence-backed current contracts and durable identity/provenance semantics; unimplemented future surfaces stay explicit and provisional. After freeze, classify additive versus breaking changes and update fixtures/client contracts together.

If a prerequisite is missing, determine whether it belongs to the current task or a bounded correction to an earlier contract. Record and propagate the repair before closing the task. No circular waits, hidden future prerequisites or silent scope reductions are permitted. The minimal local job/receipt/event/pin foundation belongs to EPIC-002; EPIC-005 consumes it for backup/export, and EPIC-006 adds provider-specific work.

A failed candidate may be repaired or replaced through an evidence-backed bounded design change. Do not silently switch billing, remove private remote access, replace Wails or bypass current host/session and data-integrity requirements to obtain a passing label. D-08/D-09 already authorize the personal-tool, directory-based and unrestricted-artifact baseline; applying them does not require a new owner approval. Provider policy changes require current supported evidence.

## Handoff

Use the [task evidence](templates/task-evidence.md), [Epic gate](templates/epic-gate.md), [decision record](templates/decision-record.md) and [change request](templates/change-request.md) as concise indexes to real artifacts. Include implemented capability, contract versions, remaining limitations and exact next task. A single CI/PR record may satisfy several references if its coverage is explicit.

## No asynchronous actions implied

These specifications do not schedule ChatGPT tasks, enroll devices, start daemons, configure networks, publish repositories or invoke providers. Installation, exposure and destructive or externally billable operations require the applicable product authorization when actually executed.
