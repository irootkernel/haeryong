### Bootstrap, identity and durability

Explicit init now records profile format 2 with storage_state=pending and opens no DB. The marker is outside the storage directory. Under the existing OS-backed profile lock, service-owned atomic/fsynced profile updates upgrade format 1 only when storage is fully empty, preserving library/profile UUIDs and the control key. Unexpected legacy contents fail recovery. New pending storage creates a private DB exclusively, then opens SQLite with mode=rw. Initial history, singleton/epochs, project and defaults commit atomically. A crash after that commit but before the ready marker reuses the committed identities rather than allocating another library.

The ready marker follows DB identity/history/health and required directory durability. Already-ready missing, zero-byte, corrupt, foreign-library/profile, unknown partial or newer databases fail without creating a substitute. Missing DB plus unknown pending storage also fails without creating one. DB, WAL and SHM files reject symlink/hardlink, ownership and permission violations. Failed Prepare closes its DB before ownership is released. The composition adapter verifies referenced/pinned filesystem bytes in bounded batches before startup readiness. Local control now reports storage.ready=true/state=ready only after this preparation; product HTTP remains unavailable.

SQLite uses one serialized connection with WAL, FULL, foreign keys and a 5000 ms busy timeout. Driver DSN initialization applies settings to replacement connections as well; actual readbacks and forced connection replacement were checked. Migration history verifies exact checksums/revision and expected tables. The tested ready-schema-1 to schema-2 upgrade first retains a coherent SQLite recovery snapshot, validates its identity/integrity, streams its checksum and syncs the recovery set. Schema 1 has no object references, so this is a metadata-only migration recovery fixture. TASK-002-01 shipped no database, and this does not claim a deployed old production DB or the complete EPIC-005 DB-plus-content backup protocol.

### Transactions, receipts and local recovery

The application requires current Authority before any lookup, then a mandatory typed AuthorizeWrite check under serialized writer ownership before receipt lookup and again before definitive commit. Scope reads expose current project lifecycle/permissions generation and configuration revision without SQL. Labelled authority fakes prove revocation during writer wait and before commit; real bearer/session policy remains a later owner.

Receipts are principal-wide across route families. Fingerprints preserve actual method/target, validated semantic body, original preconditions and omission markers plus the once-persisted normalization context. Body ordering/header case and absent/empty precondition maps normalize consistently. Matching completed or failed responses replay before stale mutation preconditions, subject to current authorization/visibility. Accepted reservations retain null definitive result/status and return stable operation lookup fields; reconciling never dispatches. A committed 202 job-creation response is completed even while the independent job runs or later fails. Resource mutation/revision, event/outbox and definitive receipt share one transaction. Events preserve stream epoch and sequence across normal restart.

Local jobs persist captured scope/config/project generations, monotonic cancel intent and attempt_generation. Claim, reassignment, accepted cancellation and process recovery fence stale success and failure. Running/cancelling/reconciling work and paused work carrying cancellation recover as interrupted; cancel intent survives and confirmed stop settles cancellation. Ordinary paused work is not implicitly retried. Terminal retries allocate linked new job identity. This is local work recovery, not external-provider outcome reconciliation.

Upload checkpoints have exactly generation, inventory_sha256, accepted_bytes (canonical decimal string) and complete_input. Initial empty checkpoints use SHA-256(empty), generation 1, bytes "0" and false. Closed purpose/target/input-mode rules preserve explicit nulls and future-consumer operation binding. Natural upload/path/offset range identity is idempotent for identical verified bytes and conflicts for changes; checkpoint/range/pin commits are atomic. Identical active seal checkpoints coalesce one job while each new completion key owns its completed 202 receipt; identical sealed input returns 200. Cancel keeps bytes/pins and reopens only after stop confirmation. Abandon immediately fences new finalization/adoption, cannot be reopened by late failure, and releases only safe upload staging pins. Historical abandoned range digests survive collection without claiming retained bytes; active ranges require a ready object and transactional upload pin. Adopted consumers and active/recovery pins remain protected.

### Filesystem and object lifetime

Content staging streams with a 64 KiB buffer and hashes/syncs the selected bytes. Under the serialized metadata transaction, a checked publication closure performs destination-local rename and directory sync, then commits ready metadata plus staging ownership. Any publication error prevents metadata commit; DB commit failure may leave a durable orphan. No whole-directory or whole-object RAM envelope is required. Same-hash replacement uses newly verified durable staging bytes; deleting metadata rejects publication/adoption before that closure.

Pins, durable references, adoption and GC reservation share SQLite serialization. Consumer reference/pin commits precede staging release. GC reserves deleting, physically removes/syncs, then finishes metadata deletion. One executor mutex covers that complete lifetime, including retry/recovery and close, so a second collector cannot reuse an in-flight reservation to delete a newly published same-hash object. Failed deletion keeps its recoverable deleting state.

Each Read owns a fresh per-invocation pin, retaining caller owner provenance without borrowing/releasing a durable job/backup pin. Overlapping reads with identical descriptors retain independent lifetimes. Verification streams into a private temporary delivery file, checks its actual digest/size, and delivers that same verified handle. Source mutation/reopening cannot substitute different bytes. Pins remain held through the callback and file cleanup, including error paths. This strategy needs temporary disk capacity for the requested object; allocation/I/O failures are explicit. Root-owned OS/filesystem/hardware compromise and universal power-loss guarantees are not claimed.
