# Authentication, device pairing and authorization

**Owner direction:** a personal developer tool with one owner and remembered devices. **Proposal:** revocable bearer sessions for local and private remote use, without a separate administrative identity system. G-AUTH remains `not_run`.

## Trust model

A service instance has one owner identity with several device sessions. Owner sessions can read and manage that owner's library, approve another device and change settings. Delete/purge, exposure, source expansion and consequential retention changes use explicit impact and confirmation flows where applicable; they do not require a second administrative grant or per-operation elevation. A confirmed automatic-purge policy authorizes the daemon to process eligible future runs. Each run still derives an exact plan and rechecks current policy and eligibility, without repeated owner confirmation unless the policy or changed conditions require it.

Haeryong trusts the owner and the generated/imported content they choose to run. Artifacts remain separate from the trusted application's origin, owner/agent credentials and native bridge. Public hostile-content hosting and containment of an unrestricted process running as the owner are outside this personal baseline.

Each owner/agent bearer is bound to its library, principal and scopes. The daemon checks current session revocation and applicable resource/workflow scope on requests. Haeryong-issued agent sessions are scoped automatically to the selected workflow and do not authorize personal review, pairing, policy changes or purge. Application scopes do not sandbox an external agent's existing OS environment. Local bootstrap remains a protected recovery path and is not passed to artifacts or deliberately supplied as model input.

`principal_id` identifies the stable owner or remembered scoped workflow within the library; it is distinct from a device session, token and transport request. The owner's identity is shared across its paired devices. A newly paired device or rotated/replacement credential for that same owner or workflow retains the `(principal_id, operation_id)` receipt namespace, so reconnecting does not silently turn recovery into a new mutation. A genuinely different workflow has its own scoped principal. Every receipt lookup or replay still authenticates the current session and rechecks its current scopes, resource visibility and lifecycle; knowing an operation ID or retaining the same principal never restores revoked authority. See the [shared registry](schema-registry.md#operation-identity-and-preconditions) and [HTTP retry rules](http-api.md#preconditions-receipts-and-retry-matrix).

## Initial local bootstrap

At first explicit initialization, create `library_id` and a local control credential/IPC endpoint with owner-only filesystem permissions. Do not expose it in arguments, URLs, package manifests or logs. Local CLI or desktop bootstrap approves the first exact pairing request. After that, any existing owner session may approve another device. Bootstrap remains available when every device is logged out or revoked.

The unauthenticated listener may serve the trusted connect screen and liveness, but no project list, private title, provider account, document counts or private assets. A loopback address, missing Origin or proxy-looking header does not create an owner session.

## Proposed pairing sequence

1. Browser POSTs a pairing request with a bounded device label. The service creates an opaque request ID, human comparison code and 256-bit random polling secret. The proposed request expiry is 5 minutes within configurable bounds. This pending-request secret stays in memory and never enters a URL.
2. The owner approves the exact displayed code through local bootstrap or an existing owner session. Show the label and creation time as descriptive context; a label alone is not the comparison code. Concurrent requests must not allow accidental approval of a merely similar device.
3. Browser polls with request ID and polling secret in the body. Successful redemption atomically consumes the request and returns one revocable bearer. Repeated or expired redemption cannot mint another session. A lost pending polling secret requires a new pairing request.
4. With **Remember device** selected by default, store the bearer in the trusted origin's localStorage. The owner may choose memory-only use for that device. Fetch `/session` with `Authorization: Bearer <token>` and continue to a validated internal route.
5. Logout revokes that session and removes the local stored token. The owner can revoke any device from another owner session. New requests fail and protected streams terminate. Disconnecting or closing a browser does not cancel accepted jobs.

Apply modest creation/polling limits and an instance-wide pending cap. Initial proposals are 5 pending requests, 2 creates/minute per reliably attributed client when available, and polling no faster than every 2 seconds. Do not trust arbitrary forwarded headers to invent client identities. Store only token/secret hashes on the server and keep codes and secrets out of logs.

## Remembered sessions and transport

| Client | Credential handling | Normal behavior |
| --- | --- | --- |
| Local browser | Revocable bearer in trusted-origin localStorage by default | Reload, new tab and browser restart reuse the device session |
| Private HTTPS browser | Same bearer flow and Remember device choice | Reuse the paired origin while its stored credential and server session remain valid |
| Memory-only browser | Bearer held in the current document | Reload or a new tab needs pairing again; accepted jobs remain durable |
| Native/CLI | Bearer or protected local control through approved OS storage/IPC | Normal process restart preserves valid owner access |
| Haeryong-issued agent session | Workflow-scoped credential or internal context | Limited to the selected import/generation/maintenance work |

The application uses one loopback listener, proposed at `127.0.0.1:9270`. Optional private HTTPS ingress proxies to that same listener. Both local and remote trusted UI use header bearers. Owner/agent management routes have no ambient cookie authentication or cookie-only recovery endpoint. No second upstream port or cookie-hostname reservation is mandatory. Configure exact expected Host and browser Origin values for the actual local and remote URLs.

localStorage is scoped by browser origin. Changing scheme, hostname or port may require pairing the new origin; normal reloads on the same origin do not. Only the trusted UI loads the stored token. It must never be passed into artifact frames, messages, URLs, copied links, referrers, logs or generated packages. Scripts deliberately installed in the trusted UI share its access; artifact code runs outside that origin.

Remembered access depends on the browser retaining its storage. Explicit site-data deletion, private browsing and platform storage policies can remove the credential without revoking the server record. If it is missing, show Connect, preserve the safe internal return route and pair through an existing owner device or local bootstrap; do not claim a daemon failure or erase accepted jobs. If storage writes fail, offer memory-only use and state that it will reconnect after the document closes. Safari's documented ITP cap concerns [seven days of Safari use without site interaction](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/), not an application-mandated seven-day login expiry. Home Screen web applications have an exception under the [WebKit policy](https://webkit.org/tracking-prevention/), but are a separate storage context: optional Home Screen use may help remembered access and does not guarantee that a browser's existing pairing transfers. Record the actual supported browser and Home Screen behavior separately. Do not add a periodic pairing requirement or assume every eight-calendar-day absence deletes storage. The owner can revoke obsolete server sessions through the existing device list.

Proposed `session_idle_seconds` and `session_absolute_seconds` default to null, meaning no automatic expiry. Sessions last until logout, revocation or application-managed restore. Positive configured limits are checked on requests and protected event delivery. `remember_device_default: true` controls the initial browser choice. Normal daemon or browser restart does not rotate sessions or require pairing.

Browser events use an authenticated fetch stream or backoff polling so the bearer stays in a header. Imports, page assets and downloads use authorized streaming transport, with resumable/chunked transfer and range retrieval where specified in the [HTTP API](http-api.md). A large file or directory export must not require a complete in-memory Blob or JSON envelope before transfer. Select and verify a browser/native download handoff that streams bytes on the supported target; a trusted-origin service-worker or platform transport is an implementation option. Do not put owner/agent bearers in EventSource, asset or download URLs. Revoke temporary object URLs when no longer needed and clear private views on logout/revocation.

## Content delivery authority

This section is the normative authority for renderer and download credentials and lifetime; the [viewer contract](viewer-protocol.md#artifact-and-trusted-host-separation) maps it to the selected browser/native construction. The trusted host automatically authorizes delivery for the selected immutable directory version or selected file/export. Normal page navigation and asset requests reuse that selection without pairing or approval per file. The renderer receives no owner/agent bearer or arbitrary management API proxy. A `context_ref` identifies stored JSON/text and grants no authorization by possession.

An optional **content-delivery credential** may authorize a narrowly scoped read when ordinary page/module/worker/media requests or a native browser download cannot carry the owner's header. It is a credential with bearer-like possession semantics, not a harmless identifier. Its opaque, unguessable value is distinct from owner/agent sessions, pairing secrets and context handles. If the selected construction uses a credential in a renderer or download URL, only this narrowly scoped content-delivery credential is permitted; owner/agent bearers remain forbidden there. Copied document links remain logical trusted-reader links without a delivery credential. Do not call such a renderer token-free. The exact transport and routes remain an EPIC-001 implementation selection. A renderer-only scoped cookie is a candidate and grants no management authority; its usability in the actual Safari embedding is an evidence question, not a promised platform capability.

A **delivery session** binds that authority to the originating owner session, library and exact version, with only the selected version's file reads or the selected immutable object/export reads permitted. It grants no management, pairing, source collection, arbitrary filesystem, context-object or other-version access. Check its binding and current owner/resource access on every protected request, including ranges and retries. Logout, revocation, configured owner-session expiry, trash/purge, application-managed restore or an observed explicit delivery close ends new protected retrieval. An authenticated host close ends the corresponding renderer delivery; a crash, lost connection or mobile background suspension is not an observed close. A separately started download has its own delivery lifetime and can continue after page navigation while current owner access remains valid.

Record the selected delivery lifetime, automatic renewal/reauthorization and closure observation before G-CONTRACT. A renewable lease may expire when its renewal signal is lost; foreground/reload recovery automatically reauthorizes the exact immutable selection through the existing valid owner session. Active delivery or download progress can renew its own authority independently of a suspended page channel. There is no total deadline for a progressing transfer and no pairing or approval per renewal. Lease expiry ends that credential's new retrieval until authorized recovery; it is not evidence that a resumable result/context upload was abandoned and never by itself authorizes staging cleanup. Current adoption and persisted transfer/job/recovery pins still govern those bytes.

Delivery state may be ephemeral and recreated after an ordinary daemon restart. Recheck current owner/resource authority and immutable identity before issuing replacement delivery authority; retaining a delivery ID or old URL alone cannot recreate it. Use existing session/state facilities and record a nonsecret correlation identity where needed, without requiring a separate persistent session platform. This restart recovery never overrides application-managed restore invalidation.

A delivery session can serve many assets and repeated Range/retry/resume requests. Consuming a one-time handoff must establish that scoped session or an equivalent resumable transport; it cannot make only the first HTTP request valid and then break ordinary asset loading or download recovery. Reauthorization retains the exact immutable content identity and rechecks scope. Store a verifier rather than a raw reusable secret where applicable, redact the credential from logs/proxy diagnostics and use a no-referrer response policy for delivery URLs. It is never author packaging metadata or model input. Record credential placement and the actual exposure of direct renderer/new-tab/download URLs to history, bookmarks, diagnostics and external requests. A no-referrer policy controls `Referer` behavior; it does not remove a credential embedded in the origin from a CORS `Origin` header, which contains no URL path ([Fetch Standard](https://fetch.spec.whatwg.org/#origin-header)). Author code may also deliberately transmit a delivery credential it receives. The selected construction must account for that narrow credential's exposure without treating it as an owner bearer or disabling ordinary networking. Already delivered or externally transmitted bytes cannot be recalled.

## Request protections

Validate the configured Host on HTTP requests. Validate a supplied browser Origin, and require an exact allowed Origin for browser pairing and mutations. Reject opaque/null origins on management routes. Valid native/CLI requests authenticate through their issued credential or local control path; absence of Origin alone grants nothing. Keep API CORS closed by default. Reverse-proxy identity and forwarding headers are not Haeryong credentials.

Use POST/PUT/PATCH/DELETE for changes. GET cannot approve devices, publish content or change personal review. Private reads, source excerpts, render bytes, directory listings, streamed/range downloads, assets, events and receipt replay require current authorization. Renderer content delivery checks the automatically established version scope rather than forwarding the management bearer into author content. Header bearers avoid the need for a cookie-session CSRF token; ordinary Host/Origin validation still applies.

Use no-store for private responses and renderers. Any selected local cache remains subject to current delivery authorization before new protected retrieval; immutable bytes alone do not justify bypassing revocation. Render notes/answers safely in the trusted UI as specified in [security](../operations/security.md). Source, project and provider selections are remembered. Rechecking the saved policy is an automatic service operation, not a per-read approval prompt.

Application-managed restore creates fresh `auth_epoch`, `runtime_generation` and `stream_epoch` values and invalidates restored device/agent sessions, delivery sessions and pending pairing requests once. Bootstrap reconnects the owner, who reviews the restore's policy impact as described in [backup and recovery](../operations/backup-recovery.md). Subsequent normal restarts reuse the new sessions. Full operating-system or VM rollback detection is not promised.

## Focused gate evidence

G-AUTH remains `not_run`. Exercise initial bootstrap, owner-session approval of a second exact code, atomic redemption, token hash storage, remembered reload/new-tab/browser-restart, optional memory-only behavior, logout/revocation, configured expiry, private GET authorization, exact Host/Origin validation and one real private HTTPS route. Verify a new device or rotated credential for the same principal can reconcile the same authorized operation receipt without repeating its effect, and that current revocation/scope restrictions still win. Verify artifact messages and URLs receive no owner/agent bearer. TASK-001-03 owns the owner-session/private-route groundwork and storage-loss checks. TASK-001-04 owns the selected renderer/download delivery proof after that groundwork: exact scope, rejection outside it, multi-request Range/retry/resume, redaction, observed closure, lease interruption and automatic authorized recovery, and termination under the rules above. It also records the trusted/render origins and actual proxy Host/Origin handling; one loopback API listener is not proof of one browser origin. Exercise storage loss and an unavailable localStorage write separately from ordinary remembered restart, including the chosen Safari device and optional Home Screen mode as separate storage contexts. An unavailable required G-VIEW device is blocked evidence, not a pass inferred from desktop behavior.

Restore testing must show that old sessions fail, one new pairing succeeds and later normal restarts retain it. These are implementation checks for the selected construction, not a new identity platform or a claim that this specification has run them.
