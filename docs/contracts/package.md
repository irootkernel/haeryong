# Result-directory package contract

**Current personal-tool baseline:** runtime schema_version "1.0" and viewer_profile "html_js_v1", documentation version 1.6.1. One AI result is a directory containing any number of HTML pages, supporting files and subdirectories. A logical document owns that directory's immutable versions. Ordinary author HTML and JavaScript remain separate from Haeryong's trusted credentials, library mutation API and native bridge. See [shared schemas](schema-registry.md), [viewer protocol](viewer-protocol.md) and the [worked example](../examples/package-example.md).

## Accepted input and optional metadata

Accept an ordinary selected directory, a ZIP containing that directory, or a single HTML/file as a convenience import. The CLI/browser handles transport preparation. The author does not need to create a manifest, assign service IDs, hash files, declare every page/region, or adopt a Haeryong interaction DSL. A single-file import includes that selected file; choose its containing directory when related local files are needed. Do not silently fetch missing local or remote dependencies to invent a complete snapshot.

Every selected file is retained with its exact bytes and relative path, including hidden files, unknown extensions and subdirectories. Preserve represented empty directories. Native/entry-aware directory input and ZIP input can represent directory entries and links; a FileList-only browser selection supplies files and their implied parent directories, not missing empty-directory or symlink information. Report the adapter's actual selection/representation before capture and offer an entry-aware, native or ZIP path when a complete directory tree is needed. Do not fabricate absent empty directories, silently omit any provided hidden entry, or claim that a platform-limited file selection captured the entire disk tree. No Haeryong maximum is imposed on an HTML file, total compressed/expanded bytes, file/page count, directory depth, authored state, input format or output size. Do not silently omit files, flatten directories, inline assets, truncate content or split one result into unrelated documents. A browser-previewable file is rendered by the available viewer; other files remain listed and downloadable. Including a native executable does not launch it.

Optional Haeryong metadata is supplied explicitly through CLI --metadata or the HTTP metadata field/resource, separately from the selected payload. A file named manifest.json, package.json or any other name inside the directory is an ordinary payload file unless the owner explicitly submits a separate metadata input. Haeryong never injects or rewrites metadata files in the author's directory. Optional metadata can enrich title/question, default page, source basis, page/region labels, references and producing-tool details. Validate fields actually supplied, rather than requiring boilerplate for files that can already be displayed. Malformed explicitly supplied metadata produces field-specific PACKAGE_INVALID or INVALID_EVIDENCE diagnostics and retains the sealed payload for correction or an explicit retry without that metadata. Correcting/removing metadata is changed semantic input and uses a new operation ID; missing optional metadata alone is never such an error.

The service inventories and hashes the selected bytes and produces immutable normalized version metadata (the generated manifest) and a file index. Publication uses the explicit request target under the [import request contract](import-workflow.md#client-association-and-import-request): missing document_id is invalid, an existing ID selects that document, and explicit JSON null allocates a new document ID once. An omitted project_id is taken only from the sealed upload target. An omitted version_id is allocated once; neither allocation consults remembered client or workflow choices. For a new document, a missing title defaults to the transport's selection_name, preserving the selected directory/file name. For an existing document, an omitted title reuses its current display title captured once in normalization_context; an explicitly supplied new title becomes the new version's immutable title_snapshot and the latest document display title at publication. Missing source metadata yields source_basis unverified and source_intent null; import remains available without calling the content source-verified. Source-grounded AI generation and answers retain their separate actual-evidence requirements.

## Remembered association and operation base

Persistent caller/profile/workflow association stores exact project/document choices, not a frozen base_version_id. CLI/UI/trusted workflow launchers resolve a new operation with the following table before transfer. The [import request contract](import-workflow.md#client-association-and-import-request) requires document_id explicitly as ID or null; the handler never resolves an omitted field from client or workflow memory. A folder path/name, title, repository or payload digest never determines document identity.

| Explicit choice for this operation | Resolved project/document |
| --- | --- |
| --document D, without --project | Resolve D and use D's actual project; ignore a different remembered project. |
| --project P with --document D | Require D to belong to P; otherwise INVALID_REQUEST. |
| --project P alone | Select P and clear the remembered document selection; create a new document in P. |
| --new-document, optionally with --project P | Clear the remembered document selection and send document_id null. Use P if supplied, otherwise the remembered/selected project. --document and --new-document together are INVALID_REQUEST. |
| No explicit association flags | Reuse the exact remembered document and its project, or create a new document in the remembered/selected project when no document is bound. |
| No explicit or remembered project/document | An owner import resolves/creates the library's stable Unfiled project. A managed workflow uses its selected project or fails if none is currently authorized; it never expands to an owner fallback or all projects. |

Missing, denied, purged or otherwise ineligible selected targets fail with the authorized reason and never become a new-document fallback. Unfiled is a normal configurable project, initially without source/disclosure settings. Existing documents keep their project; v1 has no document-move operation.

For a new document, base_version_id is null and --base-version is invalid. For an existing document, normal CLI/UI use --base-version or capture latest once before upload, preserve it in the caller journal and send it explicitly to POST /imports. A later independent operation can capture a fresh base while reusing the remembered document. A low-level API caller may instead deliberately omit base_version_id; the handler captures latest once at the first valid POST /imports reservation, not during upload creation or sealing. Retries reuse the original base and omission markers. Recheck that base at publication; stale base is VERSION_CONFLICT and a changed base requires a new operation. Identical payloads alone never merge separate new-operation intents.

| Normalized service field | Rule |
| --- | --- |
| schema_version / viewer_profile | Supported runtime schema string and html_js_v1; the unfrozen baseline remains 1.0 |
| document | Service id, project_id, title and optional question; the request supplies an existing document_id or explicit null. Only null creates a new ID once. The project must match the sealed upload target; client-side association is resolved before transfer. |
| version | Service id, nullable base_version_id, nullable source_intent and timestamps; immutable after publication |
| source_basis | unverified or evidence_recorded; evidence_recorded means supplied evidence was recorded, not that every claim is true |
| content | Nullable default_page, inventory resource identity and payload_sha256; the entire file inventory need not be embedded in this metadata response |
| content.external_dependencies | Optional known script/module/style/CDN URLs, version labels or integrity metadata; a reproducibility note, not a network allowlist |
| pages / regions | Optional labels and page-scoped anchors; the service discovers HTML paths independently, and runtime regions need not exist before scripts run |
| sources / evidence | Optional exact source/capture records for source-backed claims; source absence does not reject arbitrary imported bytes |
| references | Optional authored exact document/version/page/region targets and their actual resolution states |
| generation | Optional tool/skill/provider/model labels, with no credentials or private reasoning |

## Directory paths and page identity

A page is identified by (version_id, page_path), where page_path is the exact normalized relative UTF-8 path from the result root. Preserve case and Unicode code points; do not case-fold, ASCII-restrict, Unicode-normalize or silently rename names. Resolve URL encoding once as specified by the viewer; query and fragment are navigation context, not part of page identity. Region identity is (version_id, page_path, region_id), so two pages may both contain a region named overview. Region IDs are nonempty Unicode strings, unique within their page, without the former slug/length restriction.

Lookup first matches the exact stored path. Only when no exact entry exists may it resolve a unique Unicode canonical-equivalent path (for example NFC versus NFD). Multiple equivalent candidates fail INVALID_REQUEST with reason ambiguous_path; no case-folded or compatibility-normalized fallback is allowed. Stored names, inventory ordering and hashes remain unchanged. Responses retain requested_path and actual resolved_path; canonical page/region identity uses the resolved entry, while navigation_path may retain the authored spelling.

Normalized stored paths use / separators, have no leading / or drive prefix, and contain no empty, . or .. segment or NUL. Input adapters preserve the actual selected names while mapping path separators into this representation; URL traversal cannot address outside the selected version. Distinct case-sensitive paths may coexist in the indexed content store even when a chosen export filesystem cannot represent both. Report that destination's actual collision or path limitation before overwriting; do not impose a universal case-fold or ASCII policy at import.

Input adapters distinguish the input format's actual separators from filename characters; for example, a literal backslash in a representable Unix filename is not silently converted into a directory separator. Decode archive names using the format's explicit supported encoding into exact Unicode, or report an unrepresentable/ambiguous name. Different input names or entry kinds that collapse to one stored path are an explicit conflict, never last-entry-wins or an implicit renamed copy. Implied and explicitly represented instances of the same directory produce one directory inventory row.

Store symlink text as an inventory entry without following it by default. Default GET file on a directory or symlink returns typed entry metadata/listing context; explicit resolve_link=true follows only in-version entries using the exact-first lookup rule, with cycle detection. A successful resolution reports requested_path, resolved_path and the resolved file's content validator. An outside, absent or cyclic target remains unresolved and returns NOT_FOUND with an authorized unresolved_link reason; it grants no filesystem read outside the snapshot. Page/region identity uses the exact resolved HTML entry path. A used alias can be retained as optional navigation_path display/context data without retargeting source or page identity; authored URL navigation still uses the loader's documented alias/base behavior. Where the chosen input/output platform cannot preserve a link or name, report the exact unsupported operation and retain an inspectable incomplete result instead of claiming a lossless completed copy. Hard-linked regular files may be captured as their actual bytes at each selected path; preserving inode identity is not required for a content snapshot.

Default page discovery recognizes .html and .htm suffixes case-insensitively while preserving the exact path's case and Unicode. An explicit supported text/html media classification may identify another file as HTML. This is preview/page classification, not a payload extension allowlist: every other selected file remains retained/listed/downloadable, and unsupported preview never rejects it.

For a route without an explicit page, initial-page precedence is the owner's valid reader preference for this exact version, the immutable version's valid default_page, root index.html, the sole HTML page, then Haeryong's directory/page listing. The reader preference is a separate mutable owner/version record; clearing it or selecting another page does not modify published metadata/payload. An explicit page link always wins. The listing is service UI, not an injected file. index.html is a convention, never a required filename. All HTML pages remain directly addressable, whether or not the author linked them from the default page.

## Streaming input, integrity and publication

The CLI uploads selected bytes; HTTP does not interpret a client path as an arbitrary daemon filesystem path. Transfer uses streaming and resumable uploads with incremental inventory/hashing, finite buffers, backpressure and per-file checkpoints. An upload may be large without fitting into one JSON body, RAM buffer, compressed archive buffer or render envelope. Cursor lists and streamed metadata make file count independent of one response's size. ZIP extraction accounts for actual bytes and reports progress; an expansion ratio or entry count alone is not a rejection rule.

Resource exhaustion, inaccessible input, corrupt archive structure, conflicting duplicate entries or a real platform inability are explicit failures with the affected stage/path. Keep completed staging inspectable/resumable where possible. Cancellation, insufficient disk or interrupted transfer never publishes a truncated or partial version. There is no fixed whole-import deadline that turns a slowly progressing large input into a size limit; stalled transfers and individual transport operations can use recoverable timeouts. Worker concurrency and provider cost policies remain separate from accepted content size.

For each regular file, SHA-256 covers its exact bytes. payload_sha256 covers the canonical UTF-8 JSONL inventory, with one array followed by LF per entry, sorted lexicographically by the unsigned UTF-8 bytes of its exact stored path. The root is implicit; include every child directory, whether explicitly represented or implied by a child path, once. Entry arrays are:

- File: [path, "file", decimal_byte_size_string, lowercase_sha256].
- Directory: [path, "directory"].
- Symlink: [path, "symlink", exact_link_text].

JSON arrays contain no insignificant whitespace. Strings retain Unicode and / unescaped, escape quote and backslash, use \b, \f, \n, \r and \t for those controls, and lowercase \u00xx for remaining U+0000..U+001F characters. UTF-8 has no BOM; no Unicode normalization or additional final blank line is applied. File sizes use canonical nonnegative decimal strings with no leading zeros except "0". This serialization makes tabs/newlines in representable filenames unambiguous. An input platform's genuinely unrepresentable filename is an explicit path error, not silent character replacement. ZIP compression/order and transport chunking do not alter payload identity.

manifest_sha256 covers the exact immutable service-generated metadata bytes, separately from the canonical inventory. supplied_metadata_sha256, when present, covers the exact optional submitted metadata bytes, retained separately. User payload files, including any manifest.json, are part of the payload inventory. Generated metadata and its self-external hash are outside the original directory, avoiding self-reference and filename collisions. Large supplied metadata and inventories can themselves be streamed or referenced by immutable objects; no mandatory giant inline manifest is introduced.

For publication, validate the explicit document_id and sealed upload target under current authority. Apply the [import request and base timing](import-workflow.md#client-association-and-import-request), not the client binding table inside the handler. New-document intent has a null base. Normal clients send the base captured before transfer; only a low-level request that omits base_version_id captures latest at its first valid POST /imports reservation. Recheck that same base at publication. Stale base returns 409 VERSION_CONFLICT without publication; an existing draft/staging result stays available for explicit resolution. Persist the original caller request and normalization_context once: allocate a document ID only for explicit null, allocate an omitted version_id once, and retain created_at, permitted defaults and normalizer/schema version. A retry through another sealed upload with identical payload/supplied metadata reuses that context before computing normalized metadata; a new transport time/upload ID cannot create a false conflict. Compare the caller's original explicit fields, omitted-field markers and semantic preconditions independently, so changed intent is not hidden by reusing generated values. Matching receipt replay precedes treating its original base as stale. Same explicit version ID and identical normalized metadata/payload returns its existing authorized publication; different immutable identity bytes return IMMUTABLE_VERSION_CONFLICT and never overwrite the published version. Human sequence numbers are service-assigned.

Stage and pin inventory rows and immutable objects incrementally; finish hashing and durable object writes before atomically making the complete version visible with its latest pointer, result receipt and outbox event. The final transaction adopts the completed staged set, rather than requiring all file rows to be generated in RAM or one long writer transaction. Reference adoption and GC reservation share short coordinated transactions. A crash cannot leave a visible half-directory. The selected input may reside on another local or external volume: stream/copy it into staging on the destination content filesystem, verify and flush there, then perform the same-filesystem final rename/publication. Do not rename directly across volumes or call copy-and-delete atomic. Content-addressed physical names and exact paths in the inventory permit case-distinct author paths even on a case-insensitive destination. A genuine destination failure is explicit; the user's input volume is not an admission restriction.

Verify and serve the same pinned immutable object. Large-object integrity may use incremental verification into immutable delivery storage or verified chunk digests before release; a raw digest header is not proof that the client checked the bytes. No full directory or large asset needs to be buffered in RAM. Ranges and retries are tied to the same immutable object and digest. Staging/read/export pins survive until their owning operation finishes or safe abort cleanup releases them. Sealed uploads can support a fresh authorized import after a base conflict without recapturing bytes when the exact purpose/project/document target remains the same and reusable is true; use a new operation ID for the changed base. A sealed handle never permits changing an existing document target into another document or new-document intent; draft-specific result targets remain tied to their own draft under [import workflow](import-workflow.md#purpose-target-and-authority). The upload view reports current availability after staging ownership transfer. Abandoning staging prevents new adoption but cannot delete an already published version or active/unknown-work pins. [Import workflow](import-workflow.md) owns target, cancel/abandon and reuse behavior; the shared registry owns the state enum. Verification cancel preserves bytes; it is not abandonment. There is no automatic total-transfer expiry.

## Normal HTML, JavaScript and navigation

html_js_v1 permits ordinary author HTML/CSS/DOM code, classic scripts, ES modules and dynamic imports, libraries/frameworks, WebAssembly, workers, normal network requests and CDN resources under the browser's CORS, permissions and platform rules. There is no JavaScript/API allowlist, mandatory DSL or all-network-deny rule. Bundling/pinning external dependencies is optional when reproducibility/offline use matters.

Load the selected page and its requested assets on demand, without a whole-directory render envelope or inline-only derivative. Preserve relative and root-relative package URLs for HTML links, scripts/modules/workers, styles, images, fonts, WASM, fetch requests, query strings and fragments. A version-specific content root must work for concurrent views; changing a global current-directory root is insufficient. Preserve authored base-URL behavior and ordinary external URLs. The [viewer protocol](viewer-protocol.md) owns exact browser history, page navigation, deep links and renderer construction.

Published local bytes and supplied dependency metadata are immutable. Live external responses may change independently; a package digest does not claim to freeze uncaptured network responses. The artifact receives no owner bearer, native Wails bridge or generic privileged host method interface. Trusted app controls perform management operations after the normal owner action. This small separation does not constrain ordinary JavaScript interactions or promise containment of every stuck third-party page.

## Optional regions and host context

Declared regions enrich labels, source bindings and stable cross-links; they are not required to import or render HTML. Ordinary DOM IDs, data-haeryong-region attributes, selected text and runtime-discovered anchors may supply best-effort page-local context. Dynamic pages need not expose regions before their scripts run. Unknown, duplicate or currently missing anchors remain unresolved at that page while the rest of the directory stays usable. No missing region is silently retargeted to a different page or version.

Host messages include the current version/page/render instance. The host checks that context and treats messages only as data. Notes/questions may attach to a whole version, a specific page, or an exact page/region with selected text/context. Whole-version personal review still covers the complete directory snapshot; visiting one page never marks the result reviewed.

Selection state is ordinary JSON, including arrays and nested objects, with no fixed field count, string length, enum count or serialized-state cap. Optional state_schema is author documentation/validation for submitted context, not a required type system. Non-JSON objects or executable callbacks are not transported as privileged code. Large text/state uses the viewer's automatically transferred context_ref instead of one oversized control message. The same purpose-bound resumable upload path can stage context/body/metadata in smaller chunks before the owning API operation adopts it; no single proxy-sized HTTP body becomes a hidden total-state limit. Chunk sizes and backpressure are implementation mechanics, not truncation or author-facing input limits. A context_ref names immutable context bound to the current scope; it is not a bearer credential or management capability. Provider context-window limits are reported separately when content is selected for an AI request; they do not reject storage or rendering.

## Source evidence, references and export

Source/evidence/reference local IDs are nonempty Unicode strings unique within their own version-local collection; database keys include version_id. Source identity, capture_status, retention_mode, current availability and bytes_origin stay separate. A Git source records repo_id, object_format and full exact_revision; a snapshot records snapshot_sha256 and capture context. Optional release_label is display metadata. selected_snapshot requires inventoried authorized bytes with the matching digest; a reference-only digest does not imply retained or reconstructible bytes.

Raw imported content without evidence remains viewable with source_basis unverified. Haeryong does not perform semantic claim classification as an import admission gate. Managed source-grounded generation and answers must identify actual evidence for material source claims and cannot label unsupported claims verified. Conceptual commentary can identify its supplied explanation basis. Requested pinned/current source checks with missing bytes report unavailable/unable_to_verify; an empty target set or explanation-only text cannot become a successful source check. Completed answer/assessment citations use the registry's observed_input/read_id or posthoc_verified/verification_id variant, with target_set_id, exact revision/snapshot and bytes_sha256. Only an actual producing-attempt input observation establishes observed_input; later target verification never rewrites immutable generation provenance or proves what an unobserved native agent read. Target-byte validity and semantic claim support remain distinct; current-source B never reinterprets immutable A evidence. Later explicit imported-evidence checks use the [HTTP verification operation](http-api.md#imported-evidence-verification), preserve author-declared capture_status and add a separate service verification overlay. Optional expected digest/excerpt is compared only when supplied; otherwise the result records limited exact-target resolution/capture, never a match against unseen output. Import-only declarations do not manufacture a service-captured freshness target.

Optional authored Haeryong references preserve exact document/version/page/region identities. Resolve under current library visibility. An unknown, absent or inaccessible target remains unresolved/unavailable without hidden title/body disclosure and without rejecting the result directory. Only eligible exact targets produce validated derived edges/backlinks; the original supplied reference remains inspectable. Ordinary hrefs need no relationship metadata. Updates, archive, trash or purge change displayed resolution state without rewriting original files or silently substituting latest.

Export a selected version as its original directory/files or an archive, preserving bytes, relative paths and represented empty directories/links where the destination can represent them. Do not require flattening, bundling, HTML rewriting or adding service metadata. Haeryong metadata and personal records are separate opt-in export outputs; their names cannot overwrite original files. Stream and pin the exact selected snapshot through verification/finalization. Unavailable dependencies or destination collisions are explicit, and incomplete output is never reported as a complete lossless export. The [CLI contract](cli.md) defines optional personal-record export scope.

## Validation result

Return structured issues with streamed/cursor continuation when needed, identifying actual corrupt bytes/archives, invalid relative addressing, malformed supplied metadata or identity conflicts. Normal JavaScript, network use, multiple HTML pages, unknown extensions, large files and many entries are not validation failures. Missing source/region/reference enrichment is visible as unverified/unresolved context, not discarded payload. Validation confirms structure/integrity and checks actually performed, not factual correctness, external dependency availability or support for executing arbitrary native/server programs.
