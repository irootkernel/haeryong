# Directory HTML/JavaScript viewer and host protocol

**Owner direction:** Haeryong manages an AI result as a directory containing any number of HTML pages and related files. Normal AI-authored HTML and JavaScript should run freely as a useful personal developer tool. **Profile:** `html_js_v1`. The owner chooses which generated/imported content to run. G-VIEW remains `not_run`; the selected construction must demonstrate useful interaction, directory navigation and separation from Haeryong management privileges.

## One normal web-content profile

`html_js_v1` permits arbitrary author JavaScript and DOM behavior, inline or packaged scripts, JavaScript modules, frameworks, WebAssembly and ordinary browser APIs. Network requests, external scripts, CDNs and remote assets are allowed under normal browser, CORS, secure-context and permission rules. There is no required declarative action language, JavaScript API allowlist, generated-script hash allowlist, profile competition or universal zero-egress requirement.

Authors may implement scenarios, simulations, charts, filters and other interaction in ordinary code. A result may contain multiple HTML pages, nested directories, shared assets and arbitrary accompanying files. No single-entrypoint, `index.html`, author-written manifest, region declaration, file-type allowlist, file-count limit, directory-depth limit or HTML/package byte ceiling is required for importing or viewing a result. Preserve unknown files for download; the browser's ability to preview a format and the provider's ability to interpret it are separate capabilities. Downloading an attachment does not automatically execute a native program.

The immutable version records the complete selected directory snapshot and any available source metadata. Absent source evidence is an unknown/unverified basis, not an import or rendering failure. Runtime dependencies or network responses can change or fail independently and are not automatically part of that stored provenance. An externally fetched value does not become verified source evidence merely because the artifact displays it. Show a useful load/error state when a required dependency is unavailable. Self-contained assets are useful for reliability, not a mandatory ban on CDNs. See [package](package.md) and [schema registry](schema-registry.md).

## Directory loading and page identity

A document is the logical result directory; a version is an immutable snapshot of that directory. A rendered page is identified by `(version_id, page_path)`, where `page_path` is the exact relative UTF-8 path of the resolved HTML entry in that version. Identical basenames in different directories remain different pages. File names are not flattened or automatically rewritten. Resolve an exact stored path first; a Unicode canonical-equivalent spelling may resolve only to a unique stored entry under the [package path rules](package.md#directory-paths-and-page-identity), without case-folding or guessing an ambiguous match. Canonical `page_path` is the actual resolved stored entry, while requested/navigation spelling remains display context. An in-version symlink alias resolves to that same canonical page/region identity. Optional `navigation_path` retains the authored alias as display/navigation context, never another page or source identity; the selected loader documents its alias/base behavior while preserving ordinary authored URL navigation.

The trusted reader uses:

`/documents/{document_id}/versions/{version_id}?page={encoded_page_path}&page_query={encoded_artifact_query}&page_fragment={encoded_artifact_fragment}#region={encoded_region_id}`

`page_query` holds the artifact query without its leading `?`; `page_fragment` holds its fragment without the leading `#`. Encode these independently from the host URL. Both are optional display/navigation context, not additional content versions or source evidence. The optional host `region` fragment requests an integrated region focus without replacing the artifact fragment. An explicit `page` or deep link wins. Opening without a page chooses the owner's valid preferred default for that exact version, then the immutable package default, conventional root `index.html`, the sole HTML page, or Files/Pages in that order. **Continue** is a separate action that resolves the version's last-opened pointer and its independently saved page position; it does not change that default-page chain. Clearing the personal preference restores the immutable/default fallback and does not edit the original directory. Multiple pages without a preferred landing page are valid. The host listing does not insert a generated file into the original result.

Ordinary local HTML links, nested relative paths, root-relative paths, query strings and fragments resolve within the same exact version. Preserve CSS URLs, modules and dynamic imports, workers, WebAssembly, fonts, media and ordinary relative fetch behavior. A root-relative `/assets/chart.js` resolves at that result's content root, not at the trusted management API. The selected origin or asset relay must maintain this mapping for concurrent versions and multiple tabs; changing a global current-directory pointer is insufficient. Absolute external URLs retain ordinary external navigation/network semantics.

In-result page links update the reader's page context and history. Back/forward navigation, copied deep links, reload and opening a local page in a new tab keep the exact version, page path and requested query/fragment. Opening another HTML file does not import it as a new document or publish a new version. File navigation, a page list and a folder view remain available when the authored pages supply no links. Known browser-displayable files may use a suitable preview; other attachments remain downloadable with their paths and bytes intact. Executable HTML/SVG/XHTML previews use the unprivileged renderer boundary, including when reached from a file API or a new tab. A download or preview must not turn author bytes into a document on the trusted application's origin.

## Incremental retrieval and integrity

`GET /versions/{id}/render-bootstrap` supplies initial context and loading information, not a serialized copy of the result. `GET /versions/{id}/files` returns cursor-based metadata; `GET /versions/{id}/file?path=...` supports streamed regular-file retrieval and ranges. A directory or symlink returns typed metadata by default. Explicit `resolve_link=true` follows only preserved in-version entries with cycle detection, reporting `requested_path`, `resolved_path` and the resolved file's validator; a resolved directory still returns listing metadata. Outside-tree, missing or cyclic link targets return `NOT_FOUND` with authorized `reason=unresolved_link`, never an outside filesystem read. The unprivileged loader uses this same resolution and canonical resolved HTML `page_path`. The first page can open without loading every page, the entire inventory or all assets into memory. Fetch additional files when requested, virtualize/paginate long file lists and stream downloads. See [HTTP API](http-api.md).

Verify server-delivered stored content incrementally before the HTML parser, script engine, source renderer or provider consumes it. A loader may hash the requested object into verified immutable delivery storage, or verify recorded chunk digests before releasing each chunk. Stream or range-read those same verified bytes under the appropriate object pin; do not verify one path and later serve a different reopened file. This does not require buffering a large file in RAM or scanning the whole directory for each page view. Corrupt or missing requested stored bytes produce an explicit content error. This immutable stored-byte delivery guarantee is distinct from authored JavaScript or Service Workers generating, fetching or caching runtime responses. Such same-version author behavior remains allowed; derived/network content does not become a verified stored object or source fact.

Small transport chunks, cursor pages, backpressure and local caches are implementation mechanisms, not limits on the total artifact or the owner's input/output. Report actual disk exhaustion, disconnection, browser failure or unsupported preview behavior with progress and recovery actions. No silent truncation, file omission, downsampling or artificial maximum replaces those outcomes.

## Artifact and trusted host separation

Artifact code executes outside the trusted application's origin and credential storage. It receives no owner or agent bearer, localStorage access to the trusted UI, bootstrap secret, authenticated management API proxy or native Wails bridge. Use a separate renderer origin/context that does not share the trusted application's owner/agent credentials, or an equivalent construction that satisfies both this boundary and the directory-loading behavior above. A same-origin frame containing author code beside the owner's stored bearer does not satisfy it.

The authenticated host arranges delivery for the selected version under the normative [content delivery authority](authentication.md#content-delivery-authority). Its selected transport must support ordinary browser-initiated page, module, worker and media requests with that exact scope and resumable lifetime. The technical mapping below cannot broaden authority into an arbitrary authenticated API/filesystem relay; `context_ref` remains a data handle.

D-10 approves the [additional private HTTPS port experiment](../operations/deployment.md#approved-additional-port-renderer-experiment) on the existing node name as the first remote candidate. Choose and test the simplest functioning construction for each endpoint in G-VIEW before G-CONTRACT. Wails and private-browser endpoints may use different constructions, provided each passes the same required version-mapping, authority and navigation behavior. Their exact origin mechanisms and construction-dependent configuration/wire slots remain TBD until that evidence. Verify actual multi-page, relative and root-relative module/worker loading before choosing an opaque frame. If that construction prevents required ordinary web behavior, use a suitable separate render origin/context. Account for CSP inheritance if using srcdoc/blob, and configure the selected execution context so inline scripts, modules, frameworks, network/CDNs and WebAssembly work as intended. Keep trusted-UI code and its response policy separate from artifact execution. A separate renderer does not imply another daemon, a mandatory second API listener or a separate OS process.

Browser origin is scheme, host and port; one loopback Go/API listener does not imply one browser origin. Distinct private HTTPS ports with exact upstream mappings are the approved first candidate; host/native routing details remain to be tested. No wildcard DNS, owner domain, wildcard certificate or second daemon is approved or required. Added private renderer ports are not a storage, file-count or single-version product limit. Conversely, a shared origin with only a version path prefix does not by itself preserve root-relative requests. Referer guesses or a mutable root cannot substitute for exact version mapping. Record trusted/render endpoint separation, asset authorization, actual proxy behavior and the trusted/renderer same-site or cross-site relationship for each selected construction. Test ordinary workers separately from Service Workers and record platform capabilities for the actual scheme/OS/WebView; neither universal support nor blanket absence is assumed. The renderer endpoint must not serve the trusted UI or management API under an artifact origin, and renderer origins do not become allowed management origins.

Authored Service Workers are allowed where the platform supports them. Their registration or replacement must not replace Haeryong's version mapping or control retrieval for another result/version. Test authored root-scope registration alongside any Haeryong mapping worker. If renderer origins are reused, prove that previous clients/workers cannot control a newly assigned version before reuse; keep an origin unavailable for reassignment while that proof is absent. A `Clear-Site-Data` response by itself is not evidence that existing controlled clients have stopped. Cross-version mixing fails G-VIEW and cannot pass by being labelled a platform limitation.

Record author localStorage/IndexedDB and worker-cache behavior across reload, browser/daemon restart and mobile background/foreground. WebKit documents [partitioned, ephemeral third-party storage](https://webkit.org/tracking-prevention/); actual storage behavior therefore depends on the selected site relationship and embedding. Make a tested persistence limitation visible without promising cross-context persistence. Authored runtime storage remains distinct from durable notes/context adopted by the service.

Browser and WebView permission behavior is normal platform behavior, including user permission prompts where supported. The embedding configuration may delegate features that require an explicit browser permission; it must not silently turn the owner's Haeryong login into permission for a device capability. A platform-limited or denied feature reports its actual state. G-VIEW does not require proof that every possible network, WebRTC, DNS or browser API is blocked.

## Wails boundary and navigation

The Wails shell remains a client of the independent Go daemon through the narrow desktop Go proxy. Record the actual trusted Wails document origin, proxy/API path and credential storage for the pinned build in TASK-001-04 / G-VIEW. That native path does not by itself require opening browser CORS or treating a renderer origin as trusted. Artifact content cannot call Go bindings, use a privileged native runtime endpoint or receive native credentials. Inspect the pinned Wails construction and verify the relevant native sender/main-frame/origin boundary, or use an artifact context without native bindings. Exercise the actual native message-handler, generated binding and privileged runtime request paths exposed by that build from a child artifact frame, including after navigation and popup creation. A handler merely being hidden by JavaScript is not evidence that native calls are rejected. A JavaScript-supplied origin field or frame nonce is not a native authorization check.

Keep the privileged Wails document on its application origin. Local result navigation stays in its unprivileged renderer with host history integration. External navigation opens in an unprivileged browser/context and does not replace the privileged document with author content. A requested external link needs no Haeryong management privilege. Record how automatic loader integration updates the host's page/query/fragment and establishes the next page channel. Back/forward must return to the expected page once rather than creating duplicate host/frame history steps; a server navigation observation alone does not report client-only fragment or history changes. Host Copy link/Open in new tab actions use credential-free logical reader links. Verify authored `target=_blank`, middle-click and supported native/browser new-tab paths against the same immutable version, logical page path, query and fragment, including client-only changes. Record any direct delivery URL exposure under [authentication](authentication.md#content-delivery-authority). Redirect behavior is topology-specific: a top-level document request may be the intended unprivileged native renderer, and a server-only redirect cannot recover an unobserved client fragment. Select and prove a mapping that preserves these behaviors. These are checks of the selected configuration, not a universal adversarial WebView research program.

## Page integration channel

Ordinary HTML needs no author-installed Haeryong SDK. The loader supplies integration automatically where supported; optional author metadata or code may add richer region/scenario context. Any bootstrap or rendering wrapper is a derivative and does not rewrite the stored/exported original files or require script sanitization. A page whose runtime cannot provide detailed selection context still renders and offers host page/version-level actions.

Use a MessageChannel or equivalent sender-bound channel created by the trusted host for each integrated rendered page instance. Bind it to the particular child window, document version, exact `page_path` and protocol schema. A local page navigation establishes a fresh channel and disposes the old one while keeping the enclosing result and reader history. Also dispose on unmount/logout. An opaque frame may have origin null, so matching origin alone is insufficient. A render nonce identifies the channel and grants no management permission.

```json
{
  "protocol_version": "1.0",
  "render_instance_id": "render-example",
  "document_id": "doc-example",
  "version_id": "version-example",
  "page_path": "flows/retry.html",
  "sequence": 4,
  "type": "region.selected",
  "payload": {"region_id": "retry", "state": {"scenario": "partial-failure", "step": 3}}
}
```

The IDs above are illustrative labels, not a schema-valid published package fixture. Validate host-bound message type, current sender/page/version identity and typed envelope/payload structure. Display context is JSON/text; only declared context-transfer payloads carry byte buffers. Ignore old-page, stale/wrong-instance messages and coalesce excessive display updates. Region IDs are page-local Unicode strings. Their identity is `(version_id, page_path, region_id)`; the same ID on another page is independent. Optional authored metadata or runtime registration can supply stable regions. Ordinary DOM IDs may provide best-effort anchors. Pages without either still render and support page/version-level notes and questions.

Host display context may contain ordinary JSON without fixed author-facing field, string, enum or total-byte caps. A selected framework's internal state does not have to fit a Haeryong schema. A page may supply an appropriate serializable selection or scenario snapshot when integrating with the host; lack of one does not block rendering. Transfer large context in chunks automatically and stage it as an opaque `context_ref` rather than placing the entire object in every control message. Bind transient page context to its originating owner/session, version, page and render instance. When an explicit Save/Ask action is accepted, the saved record or job adopts the immutable context and its lifetime pins. Subsequent reads use current authorization for that record and do not require the originating session or render instance to remain alive. Loading a page or sending display context does not start an AI request or save personal review. Until the owner chooses a host action, context may remain local. See the [schema registry](schema-registry.md) for context storage and lifecycle.

| Direction/type | Payload | Host behavior |
| --- | --- | --- |
| child `viewer.ready` | profile and optional page-local region context | Confirm the loaded page instance |
| child `region.selected` | page-local region ID or fallback selection, optional text and state/context_ref | Update reader context; Ask/Notes/Review remain host actions |
| child `state.changed` | page-local selection and JSON display state/context_ref | Track the selected scenario as display context, not source evidence |
| child `reference.requested` | known optional library reference ID | Resolve a known library reference through normal authorized host navigation |
| child `viewer.error` | plain error code/message, optional details context_ref | Show a readable error and recovery action |
| host `region.focus` | page-local region ID | Request focus/highlight within the selected page |
| host `theme.set` | named theme and presentation tokens | Update artifact appearance without passing owner/agent or delivery credentials |

### Large context transfer messages

The automatic loader uses the same sender-bound page channel for large context. All messages retain the envelope's protocol, render-instance, document/version/page and sequence identity. A host-generated or loader-generated `transfer_id` identifies one immutable serialized snapshot within that channel; it is not an author-required ID or a credential. A changed snapshot starts a new transfer. Chunk payload bytes are transferable byte buffers rather than a giant JSON control message. Their offsets and digests refer to the exact UTF-8 serialized JSON/text bytes, not JavaScript string indices. The incremental path can serialize/stage a stable snapshot without requiring one complete string or ArrayBuffer in memory.

For an already materialized snapshot, loader and host may negotiate a simpler transferable-ArrayBuffer fast path with the same sender binding, media type, complete-byte digest and sealed-result semantics. Freeze any optimized envelope only after G-VIEW evidence and reflect it in the shared schema; no new message name is prescribed here. The bounded-memory incremental path remains available without an author-facing size threshold. [Transfer semantics](https://html.spec.whatwg.org/multipage/structured-data.html#structureddeserializewithtransfer) do not establish guaranteed zero-copy across every browser/WebView process boundary; measure the actual target.

| Direction/type | Payload | Receiver rule |
| --- | --- | --- |
| child `context.transfer.begin` | `transfer_id`, `media_type` for JSON or UTF-8 text | Bind one transfer to the current page instance; identical replay returns progress, changed media/context binding conflicts |
| child `context.transfer.chunk` | `transfer_id`, `offset`, `bytes`, `bytes_sha256` | Verify chunk digest and accept contiguous bytes; identical accepted offset/bytes replay, changed bytes or a gap is rejected |
| child `context.transfer.end` | `transfer_id`, `bytes_sha256` of the complete serialized snapshot | Declare end-of-input, verify contiguous bytes and final digest, validate JSON/text and seal; identical completion replay returns the same result |
| child `context.transfer.abort` | `transfer_id` | Stop unadopted transfer work and acknowledge closure; no deletion of an already adopted record |
| host `context.transfer.ack` | `transfer_id`, `next_offset`, `credit_bytes` | Report the contiguous accepted position and current flow-control credit; the loader sends only within that credit |
| host `context.transfer.ready` | `transfer_id`, `context_ref`, `bytes_sha256` | Return the sealed context handle for this page instance; the handle itself grants no access |
| host `context.transfer.error` | `transfer_id`, `code`, `retryable` | Report a typed transfer failure without a successful context reference; recoverable replay begins with the same transfer identity |

Chunk size, queue credit and idle recovery are internal transport controls. They impose no total context-byte, field, string or progressing-transfer deadline. Backpressure pauses production or staging; it does not silently keep a prefix as complete. A chunk acknowledgement describes temporary receiver flow-control state, not a saved note/question or a durable HTTP upload receipt. HTTP upload status owns durable resume/checkpoints; the frame channel needs no second persistent chunk ledger. If a receiver restarts or loses local state, report interruption, reconcile any service-staged bytes through HTTP and reconstruct missing input rather than inventing acknowledged durable bytes.

The trusted host may keep context local until transfer/staging is needed; a `context.transfer.ready` reply requires an actual service-sealed context object. It stages through authorized `purpose=context` transport and automatically generates and preserves the HTTP operation/upload identities for that logical transfer, using its own header credential. The child receives no owner bearer, generic upload proxy or arbitrary target selector. Staging uses the same serialized bytes/digest. A ready `context_ref` echoed by `state.changed` or `region.selected` must belong to the current owner/session/version/page/render binding; possession of another handle cannot import its context.

Explicit Save/Ask remains a separate host action and idempotent mutation. Before acknowledging acceptance, its transaction adopts the sealed context and transfers the required lifetime pin to the saved record or job. Replaying the action reuses that adoption. Until then the host retains any local bytes needed to stage it and displays pending state, not Saved. Channel disposal can release only temporary buffers no longer needed by pending staging or actions; durable staging follows the [upload lifecycle](http-api.md) and current persisted pins. An authorized explicit abort/abandonment may make only unadopted, unpinned work eligible for cleanup; neither disposal nor logout proves that a pending or unknown-outcome Save/Ask failed. Recheck adoption and active transfer/job/copy/recovery pins atomically before cleanup, including a navigation racing with Save/Ask; an accepted action wins its required object lifetime. No automatic staging expiry is enabled by default. A lost heartbeat, expired delivery lease, crash or mobile background suspension never by itself proves upload abandonment. Any configured cleanup policy must preserve resumable acknowledged staging and reclaim only proven inactive unreferenced work under its recorded ownership/abandonment rules. It is not a content admission limit or personal-note retention rule.

Ordinary local HTML navigation needs no declared library reference. There is no generic privileged postMessage operation. Review, deletion, settings, publication, source collection, arbitrary authenticated fetch and shell/native calls are not viewer messages. A forged reference does not expand source access. Host-owned controls stay visually and semantically outside the artifact. Reviewing an exact version concerns the complete result directory; reading or focusing one page never marks other pages or the whole version Reviewed.

## Lifecycle and recovery

When access is revoked or a document becomes trash, the host closes the affected renderer and its delivery session and stops new protected retrieval. Handle stream invalidation and current-state resynchronization even if a normal content fetch is now denied. Logout removes the remembered owner bearer for that device, ends associated delivery authority and clears protected host views. A saved note/question keeps its adopted context under the record's own authorization; renderer cleanup must not erase it. Actual browser storage loss follows the reconnect path in [authentication](authentication.md), without claiming that a remembered session can override browser storage policy.

An artifact may hang, allocate more memory than the device can supply, fail to load a dependency or crash its rendering context. Do not promise CPU, memory or process containment, or that a shared WebView can always keep host controls responsive. Provide error/reload/close recovery where available and a documented desktop/app restart path for an unresponsive context. Durable service jobs and saved data survive ordinary UI recovery. A failed page does not corrupt its sibling files or the stored version. Information already displayed or sent to an external service cannot be recalled.
