# ADR-001: Independent service and native client

**Status:** proposed, not yet implementation-validated  
**Requirement IDs:** R01 R28 R30  
**Gate:** G-STACK

## Source context

Revision 4: One shared daemon per user; Keep the daemon independent of the UI. The unchanged concept is in [sources](../sources/haeryong-concept-proposal-v4.md). This ADR elaborates the direction and must not be treated as an independent owner approval.

## Decision proposal

Use a headless Go service/CLI module with separate Wails module and shared frontend adapters. Only the service owns DB writes, durable jobs and schedules. The service stores complete result-directory versions and streams selected files; the Wails and browser clients load pages/assets as needed without pulling an entire directory into a desktop binding or JSON response.

## Alternatives and tradeoffs

An embedded desktop-owned server ties remote availability to window lifetime. Wails server mode is not the daemon baseline; desktop bindings cannot be exposed as a substitute for the versioned authenticated Go API.

## Consequences

A second executable requires matching version discovery and packaging, without microservices or separate data stores. Pin the selected supported Wails release, matching runtime/frontend dependency versions and build profile as one tested combination; record the actual Go/OS/WebView versions. A beta label neither establishes nor disproves the required boundary. Headless dependency checks exclude Wails.

Check intended native bindings, listener and normal HTML/JavaScript behavior using the pinned build. Artifact child frames and navigated/popup contexts must not invoke native message handlers, generated bindings or privileged runtime routes; verify the native sender/frame/origin check or choose a context without those bindings. Repeat the focused native-boundary, file-preview and multi-page/module/worker checks when that runtime/configuration changes. A universal browser/network containment platform is not required. G-STACK and G-VIEW remain not_run until implementation evidence exists.

## Validation and adoption

Apply [the detailed contract](../architecture.md) and record the actual evidence in the relevant EPIC-001 task before closing G-STACK. Update this record to accepted only after the decision and evidence are reviewed. If a future implementation changes an invariant or owner direction, use a bounded change request rather than silently editing historical source text.
